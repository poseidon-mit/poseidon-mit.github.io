## 1. 方法論のコアモデル（v1.0から継承）

以下3原則はv1.0で確立済みであり、v2.0でも不変である。

1. **認知的多様性の制度化** — 異なるモデルファミリーの組み合わせによるバイアス排除
2. **生成者≠レビュアーの分離** — 自己レビューの構造的限界の回避
3. **反復的収束** — 計画→レビュー→修正ループによる品質向上

---

## 2. 適用判断：3段階のパイプライン

v1.0では全タスクに7Phase固定で適用していたが、これはオーバーキルになるケースがある。タスクの複雑度に応じて3段階を使い分ける。

### 判断基準

```
意思決定の不可逆性が高い？ ──Yes──→ Full（7 Phase）
       │No
成果物に複数の利害関係者がいる？ ──Yes──→ Standard（5 Phase）
       │No
単一の正解が存在しない？ ──Yes──→ Standard（5 Phase）
       │No
                                          Light（3 Phase）
```

| レベル | Phase構成 | 所要時間目安 | 適用例 |
|--------|----------|------------|--------|
| **Full** | 全7 Phase | 4〜8時間 | Web再構築、事業戦略、製品アーキテクチャ |
| **Standard** | Phase 1→2→3→4→5（レビューは統合Phase内で実施） | 2〜4時間 | プレゼン作成、技術設計文書、マーケティング戦略 |
| **Light** | Phase 1→3→5（価値定義は口頭/暗黙、統合は人間判断） | 1〜2時間 | ブログ記事、社内報告書、単機能の技術実装 |

## 3. 操作手順（Full Pipeline）

### 前提：ディレクトリ構造

プロジェクトごとに以下の構造を作成する。中間成果物の散逸を防ぎ、再現性を担保する。

```
{project-name}/
├── 00_brief/
│   └── project-brief.md          ← プロジェクト概要（人間が記述）
├── 01_research/
│   ├── research-gemini.md
│   ├── research-claude.md
│   ├── research-perplexity.md
│   └── research-synthesis.md     ← リサーチ統合（Phase 1出力）
├── 02_value/
│   └── value-definition.md       ← 価値定義書（Phase 2出力）
├── 03_ideation/
│   ├── idea-model-a.md
│   ├── idea-model-b.md
│   ├── idea-model-c.md
│   └── ideation-comparison.md    ← 比較マトリクス（オプション）
├── 04_synthesis/
│   ├── synthesis-draft.md
│   └── synthesis-review.md       ← 統合レビュー結果
├── 05_plan/
│   ├── plan-v1.md
│   ├── review-v1.md
│   ├── plan-v2.md
│   ├── review-v2.md
│   └── plan-final.md             ← 最終計画
└── 06_log/
    └── decision-log.md           ← 各Phaseでの判断根拠の記録
```

### Phase 1: 環境認識（Deep Research）

**入力**: `00_brief/project-brief.md`
**出力**: `01_research/research-synthesis.md`

#### Step 1.1: リサーチクエリの設計

プロジェクトブリーフから、以下の3軸でリサーチクエリを生成する。

```
軸1: 市場・トレンド（「{領域}の2025-2026年トレンドと今後の予測」）
軸2: ベストプラクティス（「{領域}のベストプラクティスと成功事例」）
軸3: 競合・代替（「{対象}の競合サービスと差別化要因の比較」）
```

#### Step 1.2: マルチソース・リサーチの実行

各クエリを**2つ以上の異なるリサーチソース**で実行する。

| ソース | 強み | 弱み |
|--------|------|------|
| ChatGPT Deep Research | 広範な情報源、構造化された出力 | ソースの明示性にばらつき |
| Gemini Deep Research | Google検索との直接統合、最新情報 | 深い分析より広さ優先の傾向 |
| Claude Web Search | ファクトチェック意識が高い、慎重な情報評価 | 検索範囲がやや狭い場合あり |
| Perplexity Pro | ソース明示、リアルタイム検索 | 深い分析よりファクト収集向き |

**操作**:
1. 軸1〜3のクエリを、少なくとも2つのソースに投入する（計6回以上のリサーチ）
2. 各結果を `01_research/research-{source}.md` に保存する
3. 結果間の矛盾・一致点を `research-synthesis.md` にまとめる

#### Step 1.3: リサーチ品質の判定

以下のチェックリストで判定する。すべてYesであればPhase 2へ進む。

- [ ] 3軸すべてに対して、少なくとも2ソースからの情報があるか
- [ ] ファクトとオピニオンが明確に区別されているか
- [ ] 情報の鮮度が6ヶ月以内であるか（テクノロジー領域の場合）
- [ ] 矛盾する情報がある場合、矛盾の理由が特定されているか
- [ ] リサーチ結果から「意思決定に使える示唆」が3つ以上抽出できるか

**ゲート判定**: 上記5項目中4項目以上Yesで通過。3項目以下の場合、追加リサーチを実施。

### Phase 2: 価値定義（Value Articulation）

**入力**: `00_brief/project-brief.md` + `01_research/research-synthesis.md`
**出力**: `02_value/value-definition.md`

#### Step 2.1: 価値定義テンプレートの記入

以下のテンプレートを、人間が記入する。AIに「書かせる」のではなく、人間が自分の言葉で書く。AIはリサーチ結果を参照しながら質問を投げかけ、人間の思考を引き出す補助に徹する。

```markdown
# 価値定義書

## 1. 解決する課題
- 誰の（ターゲットユーザー）:
- どんな課題を（具体的ペイン）:
- なぜ今解決すべきか（緊急性/重要性）:

## 2. 提供する価値
- コア価値（1文で）:
- 副次的価値（最大3つ）:

## 3. 差別化要因
- 競合と比較した際の独自性:
- 模倣困難性の根拠:

## 4. 成功の定義
- 定量指標（KPI）:
- 定性指標:
- 達成期限:

## 5. スコープ制約
- 含めるもの:
- 明示的に含めないもの:
- 未決事項:
```

#### Step 2.2: 価値定義の品質判定

- [ ] コア価値が1文で表現できているか（2文以上なら焦点が分散している）
- [ ] 「含めないもの」が3つ以上明記されているか（スコープクリープ防止）
- [ ] 成功指標が検証可能な形（数値・期限付き）で定義されているか
- [ ] Phase 1のリサーチ結果と整合しているか（市場が求めていないものを定義していないか）

**ゲート判定**: 全4項目Yes。1項目でもNoなら修正して再判定。

**Phase 2が弱いと全体が崩壊する理由**: Phase 3以降のすべての判断基準がここに依存する。価値定義が曖昧だと、Phase 4の統合で「何を基準に選ぶか」が不明になり、反復ループが収束しなくなる。v1.0 §2 Phase 7の「収束しない場合の対処」が「Phase 2に戻れ」と指示しているのはこのためである。

### Phase 3: 多視点案出し（Divergent Ideation）

**入力**: `01_research/research-synthesis.md` + `02_value/value-definition.md`
**出力**: `03_ideation/idea-model-{a,b,c}.md`

#### Step 3.1: ブリーフの作成

Phase 1とPhase 2の出力を統合し、以下の形式で標準ブリーフを作成する。このブリーフは全モデルに同一のものを与える。

```markdown
# 案出しブリーフ

## 背景コンテキスト
{Phase 1 リサーチ統合の要約: 市場トレンド、競合状況、ベストプラクティス}

## 価値定義（北極星）
{Phase 2 価値定義書の全文}

## 制約条件
- 技術的制約: {あれば記述}
- 予算・リソース制約: {あれば記述}
- 時間制約: {あれば記述}

## 要求事項
上記を踏まえ、{対象タスク}について3つ以上の異なるアプローチを提案してください。

各アプローチについて以下を含めること：
1. コンセプト名と1文サマリー
2. 具体的な実現方法の概要
3. 価値定義との整合性の説明
4. 強み（最大3つ）
5. 弱み・リスク（最大3つ）
6. 実現に必要なリソース・期間の概算
7. このアプローチが最適となる条件
```

#### Step 3.2: 独立した案出しの実行

**最重要ルール**: 各モデルの出力を他のモデルに見せない。これにより独立性を担保する。

**2026年3月時点の推奨モデル配置**:

| 役割 | 推奨モデル | 選定根拠 |
|------|-----------|----------|
| Model A: トレンド整合型 | Gemini 2.5 Pro / Gemini 3.1 Pro | Google検索統合による最新情報との整合性。大コンテキスト窓による複雑なブリーフの完全処理 |
| Model B: 構造・実装型 | Claude Opus 4.6 | 深い推論能力。技術的実現可能性を自然に考慮する傾向。長文脈の一貫性 |
| Model C: 創造・体験型 | GPT-5.4 Extra High / GPT-o3 | 創造的発想。既存パターンからの逸脱。ユーザー体験視点の強さ |

**操作**:
1. 標準ブリーフを3モデルに同時投入
2. 各モデルの出力を `03_ideation/idea-model-{a,b,c}.md` に保存
3. 出力を読み比べ、以下を判定:
   - 3モデルの案に十分な多様性があるか
   - いずれかのモデルが価値定義から逸脱していないか

#### Step 3.3: 収束検出と対処

**もし3モデルの案が類似していた場合**（これは「合意」ではなく「共通バイアス」の兆候）:

```
対処法1: 制約反転法
 →「{共通している方向}とは逆のアプローチを提案してください」と
   1つのモデルに追加指示

対処法2: ペルソナ差異化法
 → 各モデルに異なる立場を割り当てる
   Model A: 「最もコスト効率の良いアプローチ」
   Model B: 「最もユーザー体験に優れたアプローチ」
   Model C: 「最も技術的に先進的なアプローチ」

対処法3: 反論生成法
 → 1つのモデルに「他の案すべてに反論する第4の案」を生成させる
```

### Phase 4: 統合（Synthesis）

**入力**: `03_ideation/idea-model-{a,b,c}.md` + `02_value/value-definition.md`
**出力**: `04_synthesis/synthesis-draft.md`

#### Step 4.1: 統合指示の投入

統合モデル（推奨: Gemini系の長コンテキストモデル）に以下を投入する。

```markdown
# 統合タスク

## 入力
### 価値定義（判断の最上位基準）
{Phase 2 全文}

### 案A（{Model A名}）
{idea-model-a.md 全文}

### 案B（{Model B名}）
{idea-model-b.md 全文}

### 案C（{Model C名}）
{idea-model-c.md 全文}

## 統合指示
上記3案を分析し、最適な統合案を作成してください。

### 必須出力構造:

#### 1. 統合案サマリー（200字以内）

#### 2. 採用要素マトリクス
| 要素 | 出典（A/B/C） | 採用理由 |
|------|-------------|----------|
| ... | ... | ... |

#### 3. 不採用要素と根拠
| 不採用要素 | 出典 | 不採用理由 |
|-----------|------|----------|
| ... | ... | ... |

#### 4. 統合案の詳細
{具体的な統合案の内容}

#### 5. 統合案のリスクと前提条件
| リスク | 影響度 | 発生確率 | 緩和策 |
|--------|-------|---------|--------|
| ... | ... | ... | ... |

#### 6. 次フェーズへの引き継ぎ事項
- 実装計画策定時に特に注意すべき点:
- 未決事項:
```

#### Step 4.2: 統合結果のクロスレビュー（v1.0からの改善点）

v1.0で指摘された「統合モデルのバイアスリスク」への対処として、統合結果を**別のモデル**に以下の形で検証させる。

```markdown
以下は、3つの案を統合した結果です。

{synthesis-draft.md 全文}

以下の観点でレビューしてください:
1. 不採用とされた要素の中に、本来残すべきだったものはないか
2. 統合によって各案の強みが薄まっていないか
3. 統合案に、元の3案のいずれにも含まれていなかった
   「統合モデルの創作」が紛れ込んでいないか
4. 価値定義との整合性は維持されているか
```

レビュー結果を `04_synthesis/synthesis-review.md` に保存。必要に応じてsynthesis-draftを修正。

#### Step 4.3: 統合品質の判定

- [ ] 採用要素マトリクスが完成しているか
- [ ] 不採用要素すべてに根拠が明記されているか
- [ ] クロスレビューで「重大な見落とし」が指摘されていないか
- [ ] 統合案が価値定義のコア価値と矛盾していないか

**ゲート判定**: 全4項目Yes。

### Phase 5: 実装計画策定（Implementation Planning）

**入力**: `04_synthesis/synthesis-draft.md` + `02_value/value-definition.md`
**出力**: `05_plan/plan-v{n}.md`

#### Step 5.1: 計画策定指示

実装計画モデル（推奨: Claude Opus 4.6）に以下を投入する。

```markdown
# 実装計画策定

## 入力
### 統合案
{synthesis-draft.md 全文}

### 価値定義
{value-definition.md 全文}

### 技術的コンテキスト（該当する場合）
{既存システムの構成、技術スタック、制約事項}

## 計画策定要件

以下の構造で実装計画を作成してください。

### 1. 実装フェーズの分割
各フェーズについて:
- フェーズ名
- 目的（1文）
- 含まれるタスク一覧
- 前提条件（どのフェーズが完了している必要があるか）
- 完了条件（Definition of Done）
- 推定所要時間
- リスクと緩和策

### 2. 依存関係マップ
- フェーズ間の依存関係をDAG（有向非巡回グラフ）として記述
- クリティカルパスを特定

### 3. リスクレジスタ
| リスク | 影響度(H/M/L) | 発生確率(H/M/L) | 検知方法 | 緩和策 | フォールバック |
|--------|-------------|---------------|---------|--------|------------|
| ... | ... | ... | ... | ... | ... |

### 4. 前提条件と制約
- 本計画が依存する前提条件
- 前提が崩れた場合の影響範囲

### 5. 未決事項
- 実装開始前に解決すべき事項
- 実装中に判断すべき事項
```

#### Step 5.2: 計画の自己チェック

計画モデル自身に以下の自己チェックを実施させる（自己レビューの限界は承知の上で、明白なミスの検出には有効）。

```
作成した計画について、以下を自己チェックしてください:
1. 各フェーズの完了条件は検証可能か（「良い」「十分」等の主観的表現はないか）
2. 依存関係にサイクル（循環参照）はないか
3. 最長のクリティカルパスは現実的な期間内に収まるか
4. 統合案の全要素が計画のどこかにマッピングされているか（漏れはないか）
```

### Phase 6: 計画レビュー（Plan Review）

**入力**: `05_plan/plan-v{n}.md` + `02_value/value-definition.md` + `04_synthesis/synthesis-draft.md`
**出力**: `05_plan/review-v{n}.md`

#### Step 6.1: レビュー指示

レビューモデル（**計画モデルとは必ず異なるモデルファミリー**を使用）に投入する。

```markdown
# 実装計画レビュー

## レビュー対象
{plan-v{n}.md 全文}

## 参照文書
### 価値定義
{value-definition.md 全文}

### 統合案
{synthesis-draft.md 全文}

## レビュー観点

以下の各観点について、問題の有無と具体的指摘を記述してください。

### 1. 論理的整合性
- フェーズ間の依存関係に矛盾はないか
- 完了条件と次フェーズの前提条件が噛み合っているか

### 2. 網羅性
- 統合案の全要素が計画にマッピングされているか
- 見落とされているステップ、考慮されていないリスクはないか

### 3. 実現可能性
- 各フェーズの所要時間見積もりは現実的か
- 技術的に非現実的な前提はないか

### 4. 効率性
- 並列実行可能なフェーズが直列に配置されていないか
- 順序の入れ替えにより効率化できるステップはないか

### 5. 価値整合性
- 計画全体が価値定義のコア価値に奉仕しているか
- スコープ外の作業が紛れ込んでいないか

### 6. リスク評価
- リスクレジスタは網羅的か
- 緩和策は具体的かつ実行可能か
- 最悪ケースシナリオが考慮されているか

## 出力形式

### サマリー判定
- **PASS**: 重大な問題なし。軽微な改善提案のみ
- **CONDITIONAL PASS**: 修正すべき問題あり（列挙）。修正後に再レビュー不要
- **FAIL**: 重大な問題あり（列挙）。修正後に再レビュー必要

### 指摘一覧
| # | 観点 | 深刻度(Critical/Major/Minor) | 指摘内容 | 修正提案 |
|---|------|---------------------------|---------|---------|
| 1 | ... | ... | ... | ... |
```

#### Step 6.2: レビュー結果に基づく判断

```
判定がPASS → Phase 7（反復終了判定）へ
判定がCONDITIONAL PASS → Critical/Major指摘を修正し、plan-v{n+1}を作成
判定がFAIL → Critical指摘を修正し、Phase 6を再実行
```

### Phase 7: 反復改善（Iterative Refinement）

#### Step 7.1: 反復の実行

Phase 5 → Phase 6 のループを繰り返す。

**反復時のルール**:
1. 前回のレビュー指摘を計画モデルに明示的に渡す
2. 修正箇所を差分で明示させる（全文書き直しは禁止）
3. 新たな修正が別の問題を生んでいないか確認する

**反復の指示テンプレート**:
```markdown
# 計画修正指示

## 前回の計画
{plan-v{n}.md}

## レビュー指摘
{review-v{n}.md}

## 修正要求
上記レビュー指摘のうち、Critical/Major判定の項目をすべて解消してください。

### 出力要件:
1. 修正後の計画全文
2. 変更箇所の一覧（変更前→変更後）
3. 各指摘への対応状況（解消/部分解消/未対応+理由）
```

#### Step 7.2: 終了判定

| 条件 | アクション |
|------|----------|
| レビュー判定がPASS | **終了**。plan-v{n}をplan-finalとしてコピー |
| CONDITIONAL PASSかつMinor指摘のみ | **終了**。Minor指摘はplan-finalに注記として付記 |
| 3回反復してもFAILが解消しない | **Phase 4に戻る**。統合案自体に問題がある可能性 |
| 5回反復しても収束しない | **Phase 2に戻る**。価値定義の曖昧さが根本原因の可能性 |

## 4. 2026年3月時点の自動化オプション

v1.0の「6.2 将来の発展方向」で言及された自動化について、現時点で実現可能な範囲を具体的に示す。

### 4.1 Claude Code サブエージェントによる並列実行

Claude Code環境では、Agentツールを使って**サブエージェントを並列起動**できる。これにより以下が可能:

**Phase 1の並列リサーチ**:
- 複数のWebSearchを同時実行し、異なる角度からの情報収集を並列化
- ただし、これはClaude内での並列化であり、異なるモデル間の並列化ではない

**Phase 5-6の高速化**:
- Claude Code内で計画策定→自己チェックまでを自動実行
- ただし、Phase 6のレビューは異なるモデルファミリーで行う必要があるため、完全自動化は不可

### 4.2 構造化出力による転送品質の向上

v1.0で指摘された「コンテキスト損失」問題への対処として、Phase間の出力をJSON/構造化Markdownで統一する。

**効果**:
- 人間が要約・編集する際の情報損失を低減
- 次Phaseのモデルが構造化されたインプットを受け取ることで、解釈のブレを低減
- ディレクトリ構造（§3前提）と組み合わせることで、中間成果物のトレーサビリティを確保

### 4.3 自動化できないもの（人間判断が必要な箇所）

以下は2026年3月時点で自動化すべきでない:

| 判断 | 理由 |
|------|------|
| Phase 2: 価値定義の記述 | プロダクトオーナーのドメイン知識と意思決定が必要 |
| Phase 3: モデル出力の多様性判定 | 「十分に異なるか」は文脈依存の判断 |
| Phase 4: クロスレビュー後の最終判断 | 統合案の方向性はビジネス判断 |
| Phase 7: 上流フェーズへの戻り判断 | 問題の根本原因特定はメタ認知的判断 |

## 5. モデル選定の原則（2026年3月改訂）

### 5.1 役割→能力要件→モデル候補のマッピング

| 役割 | 必要能力 | 2026-03推奨 | 代替候補 |
|------|---------|------------|---------|
| リサーチャー | Web検索統合、ファクトチェック | Gemini Deep Research, Perplexity Pro | ChatGPT Deep Research, Claude Web Search |
| 発散的思考者A | トレンド整合、情報統合 | Gemini 3.1 Pro | Gemini 2.5 Pro |
| 発散的思考者B | 構造的推論、実装意識 | Claude Opus 4.6 | Claude Sonnet 4.6（コスト最適化時） |
| 発散的思考者C | 創造的発想、体験設計 | GPT-5.4 Extra High | GPT-o3 |
| 統合者 | 長コンテキスト、比較分析 | Gemini 3.1 Pro | Claude Opus 4.6 |
| 実装計画者 | 構造的分解、コード理解 | Claude Opus 4.6 | Claude Code（直接実行時） |
| レビュアー | 批判的思考、盲点検出 | 計画者と**異なるファミリー** | — |

### 5.2 モデル入れ替え時の判断基準

特定のモデルが非推奨になった場合、以下の基準で代替を選定する:

1. **同一ファミリー内のアップグレード**（例: Opus 4.6 → 次期Opus）は無条件で適用
2. **異なるファミリーへの変更**は、少なくとも1つのテストタスクで出力品質を比較してから適用
3. **生成者とレビュアーの分離原則**は、モデル入れ替え後も必ず維持する

## 6. 適用パターン別クイックスタート

### 6.1 Web再構築（Full Pipeline）

```
Phase 1: トレンド分析 × 3軸 × 2ソース以上
Phase 2: Poseidon価値定義書の作成/更新
Phase 3: Gemini + Claude + GPT で設計案を独立生成
Phase 4: Gemini で統合 → Claude でクロスレビュー
Phase 5: Claude で実装計画策定
Phase 6: GPT でレビュー
Phase 7: 反復（目安2-3回）
```

### 6.2 プレゼンテーション作成（Standard Pipeline）

```
Phase 1: テーマに関するDeep Research × 2回
Phase 2: 目的・聴衆・Key Takeaway の明文化
Phase 3: 3モデルにストーリー構成案を生成させる
Phase 4: 最適な構成に統合（統合時にレビューも実施）
Phase 5: Claude でスライド単位の詳細設計
```

### 6.3 技術設計文書（Standard Pipeline）

```
Phase 1: 関連技術のベストプラクティスと制約を調査
Phase 2: 設計の目的・品質属性の優先順位を明文化
Phase 3: 各モデルに異なる設計哲学でアーキテクチャ提案させる
Phase 4: トレードオフを明示した統合設計案を作成
Phase 5: Claude で詳細設計 + ADR（Architecture Decision Record）
```

### 6.4 ブログ記事・報告書（Light Pipeline）

```
Phase 1: テーマの最新情報をリサーチ
Phase 3: 2-3モデルにアウトライン案を生成させる
Phase 5: 最良のアウトラインを選択し、Claude で本文を作成
（Phase 2は口頭レベルで省略、Phase 4は人間が直感で選択）
```
