## Phase 0: 価値の壁打ち（Value Elicitation）— v2.1新設

**入力**: 人間の頭の中にある曖昧なアイデア
**出力**: `00_brief/project-brief.md`（構造化されたプロジェクトブリーフ）
**担当**: 汎用対話モデル（Claude / GPT / Gemini いずれでも可）

### なぜPhase 0が必要か

v2.0のPhase 2（価値定義）は「人間がテンプレートを穴埋めする」形式だったが、これには2つの問題がある。第一に、人間が自分のアイデアの前提を言語化するのは認知的に高負荷であり、品質が属人化する。第二に、テンプレートの項目を見て「何を書くべきか」を考える行為は、実は「何を考えるべきか」の自己認識を前提としており、この前提が成立しない場合が多い。

AIによる逆質問（壁打ち）は、人間の暗黙知を引き出す手段として有効である。ただし、以下の制約を設ける。

### Step 0.1: 壁打ちセッションの開始

AIに以下の指示を与える:

```markdown
# 壁打ちセッション指示

## あなたの役割
私のプロジェクトアイデアを「価値定義テンプレート」の形式で
完全に言語化するための面接官。

## ルール
1. 1回の発話で質問は最大2つまで
2. 私が答えるたびに、現時点の価値定義ドラフトを更新して表示する
3. 矛盾や曖昧さを発見したら指摘する
4. 「なぜそれが重要か」「誰にとって重要か」を繰り返し掘り下げる
5. 以下のテンプレートの全項目が埋まったら終了を提案する

## 価値定義テンプレート（埋めるべき項目）
1. 解決する課題（誰の/どんな課題を/なぜ今）
2. 提供する価値（コア価値1文 + 副次的価値3つ以内）
3. 差別化要因（独自性 + 模倣困難性の根拠）
4. 成功の定義（定量KPI + 定性指標 + 達成期限）
5. スコープ制約（含めるもの/含めないもの/未決事項）

## 開始
まず、プロジェクトについて自由に話してください。
```

### Step 0.2: セッションの進行

人間はアイデアを自由に話す。AIは構造化しながら不足を質問で補う。

**品質判定**: テンプレートの全5項目が埋まり、人間が「これは自分の意図を正確に表現している」と同意したら終了。

### Step 0.3: ブリーフの保存

壁打ちの最終出力を `00_brief/project-brief.md` として保存。

**Phase 0 → Phase 2 の関係**: Phase 0の出力は「ラフなブリーフ」であり、Phase 1のリサーチ結果を踏まえてPhase 2で正式な価値定義書に精緻化される。Phase 0はPhase 2を置き換えるのではなく、Phase 2の入力品質を向上させる前処理である。

## Phase 8: 監督付き実行（Supervised Execution）— v2.1新設

**入力**: `05_plan/plan-final.md` + `02_value/value-definition.md`
**出力**: 実行済み成果物 + `06_execution/exec-log-v{n}.md`

### Phase 8が「自律的実行」ではなく「監督付き実行」である理由

v3.0提案では「自律的実装（Agentic Execution）」としていたが、以下の理由で「監督付き」に再設計した。

1. **計画書に書ききれない暗黙知**: 既存コードとの整合、環境固有の設定、ライブラリ間の互換性問題など、plan-final.mdには記述されない情報が実装時に大量に必要になる
2. **エラーの連鎖リスク**: 自律実行では初期の判断ミスが後続ステップに伝播し、手戻りコストが指数的に増大する
3. **品質と速度のトレードオフ**: 人間が各ステップの出力を確認することで、品質を犠牲にせず進められる

### Step 8.1: 実行単位の分割

plan-final.mdのフェーズ/タスクを、以下の基準で**実行チャンク**に分割する。

```
実行チャンクの粒度基準:
- 1チャンク = 人間が5-15分で成果を確認できる範囲
- 1チャンクの出力が明確に検証可能であること
- チャンク間の依存関係が明示されていること
```

### Step 8.2: チャンク単位の実行

各チャンクについて、以下のサイクルを実行する。

```
┌→ [指示] 人間がエージェントにチャンクの実行を指示
│     ↓
│  [実行] エージェントがコード生成/ファイル操作/ビルド等を実行
│     ↓
│  [報告] エージェントが実行結果を報告（成功/失敗/判断が必要な分岐）
│     ↓
│  [検査] 人間が出力を確認
│     ↓
│  [判定]
│   ├─ OK → 次のチャンクへ
│   ├─ 軽微な修正 → 修正指示を出して再実行
│   └─ 重大な問題 → Phase 5に戻り計画を修正
└────────────────────────────────┘
```

### Step 8.3: 実行ログの記録

各チャンクの実行結果を `06_execution/exec-log-v{n}.md` に記録する。

```markdown
# 実行ログ v{n}

## チャンク {m}: {タスク名}

### 指示内容
{エージェントに与えた指示}

### 実行結果
- ステータス: 成功 / 部分成功 / 失敗
- 生成/変更されたファイル: {リスト}
- ビルド結果: Pass / Fail（エラー内容）
- テスト結果: Pass / Fail（失敗テスト）

### 人間の判定
- 判定: OK / 修正指示 / 計画差し戻し
- コメント: {判断の根拠}

### 所要時間
- エージェント実行: {分}
- 人間レビュー: {分}
```

### Step 8.4: 実行品質のゲート判定

plan-final.mdの全フェーズの実行が完了した時点で:

- [ ] 全チャンクのステータスが「成功」であるか
- [ ] ビルドがエラーなく通るか
- [ ] 自動テスト（存在する場合）が全パスするか
- [ ] plan-final.mdの全「完了条件」が満たされているか

**ゲート判定**: 全項目Yes → Phase 9へ。いずれかNo → 該当チャンクの再実行。

## Phase 9: 多次元レビュー（Multi-Dimensional Review）— v2.1新設

**入力**: Phase 8の実行済み成果物
**出力**: `06_execution/review-functional-v{n}.md` + ドメイン拡張モジュールが定義する追加レビュー

### Step 9.1: 機能レビュー（全ドメイン共通）

実装モデルとは**異なるモデルファミリー**で、成果物の機能的品質をレビューする。

```markdown
# 機能レビュー指示

## レビュー対象
{成果物の説明と提供方法（コードならリポジトリパス、ドキュメントならファイルパス）}

## 参照文書
### 価値定義
{value-definition.md}

### 実装計画
{plan-final.md}

## レビュー観点

### 1. 計画との整合性
- 計画の全ステップが実装されているか
- 計画にない実装が追加されていないか（スコープクリープ）

### 2. 品質
- エッジケースの処理は適切か
- エラーハンドリングは十分か
- パフォーマンス上の明らかな問題はないか

### 3. 価値実現
- 実装された成果物は、価値定義のコア価値を体現しているか
- ユーザーが価値を実感できる状態になっているか

## 出力形式
- **PASS**: 機能的に問題なし
- **CONDITIONAL PASS**: 修正すべき問題あり（列挙）
- **FAIL**: 重大な機能的問題あり（列挙）
```

### Step 9.2: ドメイン固有レビュー（拡張モジュールが定義）

ドメイン拡張モジュールが適用されている場合、追加のレビュー観点を実行する。具体的な手順は§5のドメイン拡張モジュールで定義。

## Phase 10: 実行反復（Execution Iteration）— v2.1新設

### Step 10.1: レビュー結果に基づく判断

```
Phase 9の判定がPASS → 完了。成果物を最終出力とする
Phase 9の判定がCONDITIONAL PASS → Phase 8の該当チャンクを修正再実行
Phase 9の判定がFAIL:
  ├─ 実装の問題 → Phase 8に戻る
  ├─ 計画の問題 → Phase 5に戻る（計画修正）
  └─ 価値定義の問題 → Phase 2に戻る（極めて稀）
```

### Step 10.2: 終了判定

| 条件 | アクション |
|------|----------|
| 全レビューがPASS | **完了** |
| 3回反復してもFAILが解消しない | Phase 5に戻り計画を根本的に見直す |
| 5回反復しても収束しない | Phase 2に戻り価値定義を再検討する |

## 4. 2026年3月時点の実現可能性マップ

v3.0提案の「自動化」主張に対し、各項目の現時点での実現可能性を正確に評価する。

### 4.1 実現可能（今すぐ使える）

| 項目 | 実現方法 | 制約 |
|------|---------|------|
| Phase 0: AI壁打ち | 任意の対話モデルで即座に実行可能 | 人間の協力が前提 |
| Phase 1: 並列リサーチ | 複数ブラウザタブで同時にDeep Research実行 | モデル間の自動突合は手動 |
| Phase 3: テキスト案出し | 3モデルに同一ブリーフを並列投入 | 各モデルの出力を手動で保存 |
| Phase 8: チャンク単位のエージェント実行 | Claude Codeでファイル操作・ビルド・テスト実行 | チャンク間は人間が監督 |
| Phase 9: コードレビュー | 異なるモデルにコードを渡してレビュー | 手動転送が必要 |

### 4.2 部分的に実現可能（制約付き）

| 項目 | 実現方法 | 制約 |
|------|---------|------|
| Phase 3: プロトタイプ生成 | 各モデルにスケルトンHTML/コンポーネント出力を要求 | 実行可能なプロトタイプになるかはモデルとプロジェクトの複雑度に依存 |
| Phase 8: 連続チャンク実行 | Claude Codeのサブエージェントで複数タスクを順次実行 | 依存関係の自動解決は不完全。判断分岐では人間介入が必要 |
| Phase 9: VLMレビュー | スクリーンショットを撮影しVLMに評価させる | 「トレンドとの照合」は主観的であり、レビュー結果の信頼性にばらつき |

### 4.3 現時点では非現実的

| 項目 | v3.0の主張 | 現実 |
|------|-----------|------|
| plan-final.mdからの完全自律実装 | 「P5の計画に基づきローカルファイルを直接読み書きして実装」 | 計画書に書ききれない暗黙知（環境設定、ライブラリ互換性、既存コード文脈）が大量に存在。チャンク単位の監督付き実行が現実的上限 |
| Phase間の完全自動転送 | 「エージェントがディレクトリを自律的に参照・更新」 | ファイル読み書きは可能だが、「どの情報をどの粒度で次Phaseに渡すか」の判断は人間のコンテキスト・エンジニアリングに依存 |
| 品質判定の完全自動化 | — | ゲート判定の「OK/修正/差し戻し」判断は、ドメイン知識とビジネス判断を要する |

## 5. ドメイン拡張モジュール

汎用コア（Phase 0-10）に対して、ドメイン固有の要件を拡張モジュールとして定義する。各モジュールは以下を規定する:

1. **Phase 3の追加出力形式**（概念実証プロトタイプの形式）
2. **Phase 8の実行環境と手順**（ビルド手順、テスト手順）
3. **Phase 9の追加レビュー観点**（ドメイン固有の品質基準）

### 5.1 Web構築モジュール

#### Phase 3 拡張: UIプロトタイプの出力

各モデルにテキスト案に加え、以下を要求する:

```markdown
## 追加出力要件（Web構築）

テキストでの概念説明に加え、以下を出力してください:
1. 主要画面のワイヤーフレーム（Tailwind CSSによる静的HTML、または
   テキストベースのレイアウト記述）
2. コンポーネント構成図（どのUIコンポーネントが必要か）

## レビュー観点

### 1. 価値表現
- UIがコア価値を視覚的に体現しているか
- ターゲットユーザーにとって直感的に操作できるか

### 2. 視覚的品質
- レイアウトの整合性（要素の配置、余白、グリッドの一貫性）
- タイポグラフィの階層（見出し・本文・補足の視覚的区別）
- 色彩の一貫性（デザインシステムとの整合）
- レスポンシブ対応の妥当性（モバイル表示を含む場合）

### 3. UXの基本
- タッチターゲットのサイズ（44px以上推奨）
- CTAの視認性
- 情報の優先順位が視覚的階層に反映されているか
- ローディング状態・空状態・エラー状態の考慮

## 出力形式
| 指摘 # | カテゴリ | 深刻度 | 具体的な指摘 | 改善提案 |
|--------|---------|--------|-------------|---------|
| 1 | ... | Critical/Major/Minor | ... | ... |
```

**Step 9.V3: 視覚レビューの判定**

```
Critical指摘が0件 かつ Major指摘が2件以下 → PASS
Critical指摘が0件 かつ Major指摘が3件以上 → CONDITIONAL PASS
Critical指摘が1件以上 → FAIL
```

## 6. クイックリファレンス

### Full Pipeline（計画層+実行層）

```
Phase 0:  価値の壁打ち      → AIの逆質問でアイデアを構造化
Phase 1:  Deep Research     → 3軸×2ソース以上の情報収集
Phase 2:  価値定義          → P0出力+P1リサーチを統合し正式定義
Phase 3:  多視点案出し      → 3モデル独立生成（+ドメイン拡張時はプロトタイプ）
Phase 4:  統合             → 最適案へ収束+クロスレビュー
Phase 5:  実装計画策定      → 具体的ステップに分解
Phase 6:  計画レビュー      → 異なるモデルで盲点検出
Phase 7:  反復改善         → P5-P6ループ（目安2-3回）
--- 実行境界 ---
Phase 8:  監督付き実行      → チャンク単位でエージェント実行+人間検査
Phase 9:  多次元レビュー    → 機能レビュー+ドメイン固有レビュー（VLM等）
Phase 10: 実行反復         → P8-P9ループ（目安2-3回）
```
